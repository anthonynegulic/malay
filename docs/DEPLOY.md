# Deploying Bukit to Vercel

Bukit is a Vite static SPA plus one Hono serverless function (`api/[...route].ts`).
Client uses hash routing, so the only server route is `/api/*`; everything else is
static from `dist`.

**How the function is built:** `server/app.ts` holds the real logic (shared with
local dev via `server/index.ts`), but the Vercel function does not import it
directly. `npm run build:api` (esbuild, see `scripts/build-api.mjs`) pre-bundles
`server/app.ts` and everything it imports into one dependency-free file,
`api/_app.generated.js`, which `api/[...route].ts` imports as a plain
same-directory sibling. This sidesteps Vercel's per-file TypeScript→JS module
resolution for cross-directory relative imports (an earlier version imported
`../server/app` directly and crashed on Vercel with `ERR_MODULE_NOT_FOUND` — the
Lambda's native Node ESM loader needs exact, already-compiled file paths, which
multi-directory relative TS imports don't reliably give it). The generated bundle
is committed to the repo *and* regenerated by every build (`vercel.json`'s
`buildCommand` and the root `npm run build` both call `build:api` first), so it's
never stale in a deploy. If you edit `server/app.ts` and only run things locally,
remember to re-run `npm run build:api` (or `npm run build`) before pushing.

**The function runs on the Edge runtime, not Node.js** — `api/[...route].ts`
exports `config = { runtime: 'edge' }`. This is required, not optional:
`hono/vercel`'s `handle()` returns a plain Fetch API `(Request) => Response`
function, and without this config Vercel invokes the default export as a
classic Node `(req, res)` handler instead, which crashes on every single
request (this was the actual cause of an earlier `FUNCTION_INVOCATION_FAILED`
that looked identical across several unrelated attempted fixes — the crash
page gives no detail because the handler never runs any of our code). If you
ever add something Node-only (fs, native modules) to `server/app.ts`, it won't
work under Edge — keep that file to fetch/Web APIs only.

## One-time setup (Vercel dashboard)

1. **vercel.com → Add New… → Project → Import** the `anthonynegulic/malay` repo.
2. Framework preset auto-detects **Vite** (build `vite build`, output `dist`) — the
   committed `vercel.json` pins this. No changes needed.
3. **Environment Variables** — add before the first deploy:
   - `ANTHROPIC_API_KEY` = your key (required)
   - `CLAUDE_MODEL` = `claude-sonnet-4-6` (optional; this is the default)
   - `APP_PASSPHRASE` = any phrase (optional but recommended — see below)
4. **Deploy.** Every push to the connected branch redeploys automatically.

Set the **Production Branch** (Settings → Git) to whichever branch you want live —
currently `claude/bukit-app-review-3hnowa`, or `main` after this is merged.

## Protecting your API credit

The `/api/generate` and `/api/grade` routes spend your Anthropic credit, and a
Vercel URL is public. Set **`APP_PASSPHRASE`** and the app will ask for it once
(stored in the browser) before it calls the API — a random visitor without the
phrase gets a 401 and can't generate anything. Reviews, the word browser, and all
local-only features keep working without it. Leave `APP_PASSPHRASE` unset for a
fully open deployment (fine for a quick private test).

## Verifying a deploy

- `https://<your-app>.vercel.app/api/health` → `{"ok":true,"keyConfigured":true,"gated":…}`.
  If `keyConfigured` is false, the env var isn't set (or you didn't redeploy after
  adding it).
- Then open the app, run a session, and hit **Baca** — the reading should generate.

## Notes

- Env vars are read at request time, so changing one only needs a redeploy, not a
  code change.
- The service worker caches the app shell; after a deploy, hard-refresh once (or
  reinstall the PWA) to pick up the new version.
- Local dev is unchanged: `npm run dev` (Vite :5173 + Hono :8787).
- If a deploy still behaves like an old build after pushing a fix (same error,
  same stack trace), force a clean rebuild: Vercel dashboard → Deployments →
  "..." on the latest → Redeploy → **uncheck "Use existing Build Cache"**. This
  rules out a stale cached function bundle rather than a real code issue.
